# 模组开发者文档

本文档面向希望为当前游戏编写模组的开发者，说明当前版本实际可用的模组能力、目录结构、开发流程和已知限制。

> 📌 **公开 SDK 版说明**：本文档同步自游戏工程内部文档，描述的是游戏当前发布版本的真实模组能力与限制，可作为开发依据。

> 说明
>
> 本文档基于 `C:\1` 当前代码实现整理。
> 如果本文档与旧设计文档冲突，请以当前代码和 `MOD_SYSTEM_CURRENT_STATE.md` 为准。

## 1. 开发前先知道

当前模组系统已经可以工作，但仍然属于“能开发、能运行、但接口边界要看清”的阶段。

你在开发前应先接受这几个事实：

- 当前模组更改通常需要重启游戏后生效
- 加载顺序以游戏保存的模组设置为准，不是单纯看 `manifest.json`
- 未拥有完整版时，模组不会被激活
- 资源覆盖、配置覆盖、本地化和部分 DLL 模组是当前最稳定的能力
- 高级 UI 替换和复杂依赖管理目前仍有边界

## 2. 当前支持的模组类型

当前版本较靠谱的模组类型包括：

- 配置覆盖模组
- 本地化模组
- 图片、模型、材质等资源覆盖模组
- 部分 Server / Client DLL 模组
- 依赖 Harmony 的逻辑补丁模组

当前不建议一上来就做的内容：

- 强依赖复杂 UI 替换的大型模组
- 假设存在完整依赖拓扑排序的模组
- 假设 manifest 中 `LoadOrder` 一定生效的模组

## 3. 模组目录结构

推荐目录结构如下：

```text
Mods/
└── YourMod/
    ├── manifest.json
    ├── Plugins/
    │   ├── Server/
    │   │   └── YourServerMod.dll
    │   └── Client/
    │       └── YourClientMod.dll
    ├── ConfigData/
    ├── Image/
    ├── Mesh/
    ├── Material/
    ├── Localization/
    ├── UI/
    └── Source/
```

说明：

- `manifest.json` 必需
- `Plugins/Server/` 放服务端 DLL
- `Plugins/Client/` 放客户端 DLL
- `ConfigData/` 用于配置覆盖
- `Localization/` 用于文本本地化
- `UI/` 用于 UI 相关资源
- `Source/` 不是运行必需，但建议保留，方便维护和发布源码

## 4. Server 与 Client 的区别

你开发 DLL 模组时，需要先判断逻辑应该跑在哪一端。

### 4.1 Server 端

适合：

- 游戏逻辑
- 数值修改
- 生态箱状态更新
- 存档相关逻辑
- 配置处理
- Harmony 补丁

放置位置：

- `Plugins/Server/`

### 4.2 Client 端

适合：

- 客户端表现
- 特效、视觉、渲染相关逻辑
- 客户端 UI 行为

放置位置：

- `Plugins/Client/`

### 4.3 选择建议

如果你只是想修改游戏核心行为，优先做 Server 模组。

如果你要改的是显示效果或客户端界面，再考虑 Client 模组。

大多数普通玩法模组，先做 Server 版会更稳。

## 5. manifest.json

一个最小可用示例如下：

```json
{
  "Id": "com.yourname.modname",
  "Name": "你的模组名称",
  "Version": "1.0.0",
  "Author": "YourName",
  "Description": "模组说明",
  "MinGameVersion": "0.1.0",
  "Dependencies": ["com.lib.harmony"],
  "Scripts": {
    "Server": ["YourServerMod.dll"],
    "Client": ["YourClientMod.dll"]
  }
}
```

### 5.1 当前稳定识别字段

当前实际稳定生效的字段主要有：

- `Id`
- `Name`
- `Version`
- `Author`
- `Description`
- `MinGameVersion`
- `Dependencies`
- `Scripts.Server`
- `Scripts.Client`

### 5.2 必填字段

当前至少应保证这些字段正确：

- `Id`
- `Name`
- `Version`

### 5.3 当前不要依赖的字段行为

当前不建议你依赖下面这些行为：

- 在 manifest 中写 `LoadOrder` 后自动生效
- 复杂依赖对象自动解析
- 所有设计文档里提到的扩展字段都被运行时识别

实际加载顺序仍以游戏保存的模组设置为准。

## 6. 加载顺序和依赖

### 6.1 当前真实规则

当前模组加载顺序主要来自：

- 游戏内模组管理界面保存的设置
- `ModSettings.json` 中记录的 `LoadOrder`

### 6.2 Dependencies 的作用边界

`Dependencies` 字段是有的，但你不能假设当前运行时已经帮你做了完整依赖拓扑排序和强校验。

更稳妥的做法是：

- 在文档里明确写出依赖项
- 在模组启动时自己检查关键依赖是否存在
- 对依赖能力缺失时给出清晰日志

### 6.3 推荐做法

如果你的模组依赖 `HarmonyLib`：

- 在 `manifest.json` 中写入 `Dependencies`
- 同时在运行时检查 `_context.HarmonyManager.IsHarmonyAvailable`

不要只依赖声明，不做运行时防御。

## 7. DLL 模组入口

所有 DLL 模组必须实现 `IModEntry`。

接口见：

- [IModEntry.cs](/C:/1/server/Assets/Scripts/Core/Mod/ModAPI/IModEntry.cs)

核心成员：

```csharp
public interface IModEntry
{
    string ModId { get; }
    string ModName { get; }
    string Version { get; }

    void Initialize(IModContext context);
    void OnEnable();
    void OnDisable();
    void OnUnload();
    void OnUpdate();
}
```

### 7.1 生命周期建议

推荐这样使用：

- `Initialize()`：缓存上下文、注册事件、做轻量初始化
- `OnEnable()`：真正启用功能、注册补丁、打开逻辑
- `OnDisable()`：移除补丁、取消事件订阅
- `OnUnload()`：清理资源
- `OnUpdate()`：只放必须逐帧处理的逻辑

不要在 `Initialize()` 里写大量阻塞式或高风险逻辑。

## 8. IModContext

`IModContext` 是模组访问系统能力的主要入口。

接口见：

- [IModContext.cs](/C:/1/server/Assets/Scripts/Core/Mod/ModAPI/IModContext.cs)

当前主要可用能力：

- `Logger`
- `AssetLoader`
- `ConfigLoader`
- `EventBus`
- `GameServices`
- `GameEvents`
- `Hooks`
- `HarmonyManager`
- `UIServices`

### 8.1 Logger

推荐所有模组都统一使用：

- `_context.Logger.Log(...)`
- `_context.Logger.LogWarning(...)`
- `_context.Logger.LogError(...)`

这样日志更容易排查。

## 9. 资源覆盖

当前会被扫描并参与覆盖映射的目录包括：

- `Image`
- `Mesh`
- `Material`
- `Animation`
- `Sound`
- `ConfigData`
- `UI`
- `Plugins`

覆盖原则：

- 相对路径相同则覆盖
- 后加载模组覆盖前加载模组

这意味着你做资源模组时，通常要镜像游戏原有目录结构。

## 10. 配置覆盖

当前配置覆盖路径为：

- `ConfigData/...`

当前实际逻辑是按 `ID` 合并 JSON 数据：

- 相同 `ID` 的项由模组覆盖
- 新 `ID` 的项会追加

因此做配置类模组时，建议：

- 尽量保持原始数据结构一致
- 使用稳定的 `ID`
- 避免无意义地整体重写大文件

## 11. 本地化模组

当前本地化能力是比较可靠的一部分。

推荐目录：

```text
Localization/
├── zh-CN.json
├── en.json
└── ...
```

你可以用它做两类事情：

- 覆盖已有文本
- 添加新语言

如果模组需要新字体，也应按当前本地化和字体加载逻辑准备对应资源。

建议先参考：

- `Mods/LocalizationExampleMod`
- `Mods/RussianLanguageMod`

## 12. Harmony 模组开发

### 12.1 Harmony 是什么

Harmony 是一个运行时补丁库，用于在不改游戏源码的前提下修改现有方法行为。

在当前项目里，它通常以 `HarmonyLib` 基础模组的形式提供。

### 12.2 当前正确理解方式

你依赖的不是“神奇自动生效的补丁系统”，而是：

- 项目提供的 `IModHarmonyManager`
- 模组内存在 `0Harmony.dll` 或等效依赖
- 你的模组主动创建补丁实例并应用补丁

### 12.3 当前实现状态

当前版本已经修复了最早期那种“只启动时检查一次 Harmony，后续永远不可用”的问题。

现在更推荐的写法仍然是：

```csharp
if (!_context.HarmonyManager.IsHarmonyAvailable)
{
    _context.Logger.LogError("Harmony 不可用");
    return;
}

var harmony = _context.HarmonyManager.CreateHarmony(ModId);
```

### 12.4 推荐做法

- 先检查 `IsHarmonyAvailable`
- 再创建实例
- 失败时给出清晰日志
- 停用模组时确保补丁可移除

### 12.5 示例

建议参考：

- `Mods/SpeedBoostMod`

## 13. 钩子与事件

### 13.1 游戏事件

接口见：

- [IModGameEvents.cs](/C:/1/server/Assets/Scripts/Core/Mod/ModAPI/IModGameEvents.cs)

当前可订阅内容包括：

- 生态箱事件
- 生物事件
- 植物事件
- 装饰物事件
- 经济事件
- 游戏保存与加载事件

### 13.2 钩子系统

接口见：

- [IModHooks.cs](/C:/1/server/Assets/Scripts/Core/Mod/ModAPI/IModHooks.cs)

当前可注册的钩子范围包括：

- 生物生成、伤害、移动、饥饿、繁殖
- 植物生长、产出
- 价格、收入
- 水质、温度、光照
- 配置加载、存档保存、存档读取

### 13.3 建议

如果一个需求可以用普通事件解决，就不要优先上 Harmony。

优先级建议：

1. 配置覆盖
2. 游戏事件
3. 钩子系统
4. Harmony 补丁

这样稳定性通常更好。

## 14. UI 模组

接口见：

- [IModUIServices.cs](/C:/1/server/Assets/Scripts/Core/Mod/ModAPI/IModUIServices.cs)

当前 UI 能力包括：

- 从 AssetBundle 注册 UI
- 从模组目录注册 UI
- 通过工厂函数动态创建 UI
- 显示、关闭、注销 UI

### 14.1 现实边界

虽然代码层面有 UI 替换和 UI 注册能力，但当前不建议把它当成“所有 UI 都能无缝替换”的成熟能力。

你开发 UI 模组时应该：

- 先做小范围测试
- 不要默认所有界面调用链都已接入替换入口
- 优先从简单独立 UI 开始

### 14.2 示例边界

`UIReplacementExample` 当前并不是完整打包示例。

如果你要做 UI 替换模组，最好自己做最小可运行验证，不要完全照着旧 README 假设它一定能直接用。

## 15. 编译建议

当前更建议你这样组织工程：

- 在模组目录保留 `Source/`
- 明确区分 Server / Client 工程
- 输出 DLL 到：
  - `Plugins/Server/`
  - `Plugins/Client/`

建议至少保留：

- 源码
- `.csproj`
- `manifest.json`
- 依赖说明

## 16. 调试建议

开发阶段建议：

- 每次只测试一个新功能
- 每次只改一个主要变量
- 启用模组后重启游戏
- 重点查看日志中的模组加载、依赖失败、Harmony 失败信息

如果模组没生效，优先检查：

1. `manifest.json` 是否正确
2. `ModId` 是否和代码里一致
3. DLL 是否放到了正确目录
4. 是否缺少依赖模组
5. 是否未拥有完整版导致被统一拦截
6. 是否改完后没有重启游戏

## 17. 当前已知限制

开发时请特别注意这些限制：

- manifest 中的 `LoadOrder` 不应假设一定直接生效
- 当前依赖关系没有完整的强制拓扑管理
- UI 替换能力代码存在，但示例并不完整
- 某些旧文档中描述的能力早于当前实现，不一定准确
- 客户端模组配置来源于服务端保存的设置

## 18. 推荐的最小开发路线

如果你是第一次给这个项目写模组，建议按下面顺序上手：

1. 先做一个只改 `ConfigData` 的配置模组
2. 再做一个本地化模组
3. 再做一个最小 Server DLL 模组
4. 最后再尝试 Harmony 或 UI 模组

这样最容易快速验证你的开发环境有没有问题。
